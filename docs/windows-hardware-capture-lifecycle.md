# Windows hardware capture cleanup

The hardware WASAPI capture owner now checks `IAudioClient::Stop` before releasing its native resources. Previously its destructor ignored a failed Stop and then released the capture service, audio client and event. The changed path fails closed when Stop does not establish that capture stopped.

An exact native endpoint ID is reserved before opening COM or an audio client. Native open checks that `IMMDevice::GetId` returns the selected ID; alternate strings resolving to the same endpoint are rejected before event creation. Logical input aliases within one session still share the existing single physical capture stream.

Every owner exit uses the same cleanup path, including cancellation, failed readiness delivery, native Start failure and packet faults. Entering Start creates a Stop obligation even when Start returns an error. A successful Stop, including `S_FALSE`, clears that obligation. A failed Stop retains the native capture service, client, event and their dependency guards without calling their destructors or retrying Stop. Quarantine never restores session publication authorization. The native references are intentionally retained until process exit; retaining an apartment guard is not proof that its original COM apartment survives the owner thread's exit.

On successful Stop, native fields are released in order: capture service, client, event, realtime guard, apartment guard. Event closure keeps its existing independent `CaptureSnapshot.event_close` result. A failed CloseHandle is attempted only once; the native client has already been released, while the endpoint reservation remains occupied. Neither a missing Stop return nor a pending or failed event close releases the reservation.

The first-fault latch continues to preserve the original fault. Stop's exact HRESULT is separately retained in the endpoint registry, independently of the graph's PCM ring and telemetry. A retry of an occupied endpoint reports a retained Stop failure first, otherwise a retained CloseHandle failure, or the pending cleanup state. Stop is not yet a separate public snapshot field; if an earlier fault already occupied the latch, the retained Stop HRESULT is surfaced on that endpoint's next start attempt. A clean Stop and event close releases admission for a subsequent start.

There are at most 64 simultaneously live or retained hardware endpoint reservations. Their charged worker-storage estimates may not exceed 256 MiB. This is **not a total retained-memory limit**: the estimate excludes opaque COM/driver allocations, and a blocked native call can keep `CaptureState` and session-wide telemetry alive, including other capture rings. These caps prevent unlimited repeated native owners, but do not provide hard recovery from a hung OS/driver call or prove a whole-process memory ceiling. Control timeouts remain bounded; owners are never forcibly joined or destroyed by the UI thread. Restarting ReLink is required to clear an unproven retained owner.

Portable controls exercise Stop obligations after failed Start, exact successful HRESULT preservation, cleanup order, failed-Stop quarantine, missing returns, independent failed CloseHandle, constructor unwind, cancellation before/after native construction, late diagnostics after graph replacement, endpoint admission, and slot/byte/overflow limits. They call no Windows APIs. Windows cross-compilation and linting check integration only. Installed Windows capture, COM behavior after failed Stop, device removal, repeated restart, timing, and long-duration reliability remain unverified.
